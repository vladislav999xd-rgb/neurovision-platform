# День 4 — ответы преподавателю

## Что появилось

Добавлена операция возврата отменённого талона в очередь. Основная функция —
`requeue_ticket(state, ticket_id)` в `student_logic.py`. Интерфейс находится в
`app.py`: отдельная карточка «Вернуть в очередь» позволяет выбрать любой талон,
поэтому функция сама проверяет и успешный, и ошибочный случай.

Сохранены возможности предыдущих дней:

1. регистрация, вызов, завершение, отмена и фильтрация;
2. перенос ожидающего талона в другой кабинет;
3. общий `state` с `records`, `history` и `extra`;
4. журнал успешных действий;
5. сохранение состояния, восстановление и выгрузка документа.

## Договор новой функции

```python
requeue_ticket(state, ticket_id)
```

Функция получает весь `state` и номер талона. Возвращает обычный словарь
действия с полями `ok`, `message` и `record_id`.

Успешное действие возможно, только если:

- талон существует;
- его статус равен `canceled`;
- его кабинет присутствует в `extra["cabinets"]`;
- в этом кабинете нет другого активного талона того же посетителя.

При успехе сохраняются `id`, `visitor_code` и `cabinet`. Статус меняется с
`canceled` на `waiting`, а `queue_order` получает `max + 1` по всем талонам.
При отказе не изменяется ни одна запись и не добавляется событие.

## Как выполняется функция по шагам

1. `find_ticket` ищет талон по `id`.
2. Если талон не найден, функция сразу возвращает отказ.
3. Проверяется точный статус `canceled`.
4. `validate_registration` повторно проверяет кабинет и активный дубль. В
   `excluded_ticket_id` передаётся номер возвращаемого талона, чтобы он не
   считался собственным дублем.
5. `next_queue_order` просматривает все талоны и возвращает максимальный
   порядок плюс один.
6. Только после всех проверок меняются `status` и `queue_order`.
7. `append_event` добавляет одно событие `requeue` с прежним и новым порядком.

## Почему у талона id=5, но queue_order=7

`id` — постоянный номер самого талона. Возврат не создаёт новый талон, поэтому
номер остаётся 5. `queue_order` — позиция поступления в общую очередь. До
возврата максимальный порядок равен 6, следовательно новый порядок равен 7.

Первого посетителя выбирает цикл в `find_first_waiting`: он рассматривает
только `waiting` нужного кабинета и сохраняет словарь с минимальным
`queue_order`. Поэтому в кабинете 101 после возврата вызовы идут 1, 2, 5.

## Событие истории

После успешного возврата создаётся событие:

```python
{
    "action": "requeue",
    "record_id": 5,
    "field": "status",
    "before": "canceled",
    "after": "waiting",
    "related_ids": [5],
    "details": {
        "old_queue_order": 5,
        "new_queue_order": 7,
    },
}
```

`event_id` назначает общий помощник `append_event`. Повторное нажатие получает
отказ, потому что статус уже `waiting`; второе событие не создаётся.

## Короткие ответы на возможные вопросы

**Почему нельзя создать новый талон?** Тогда изменится `id`, а по заданию
возвращается прежнее обращение.

**Почему проверка выполняется до изменения?** Иначе при отказе пришлось бы
откатывать часть данных, и функция могла бы оставить повреждённый `state`.

**Почему в `next_queue_order` учитываются done и canceled?** Порядок должен быть
глобально уникальным и всегда увеличиваться.

**Что произойдёт при повторном клике?** Функция увидит `waiting`, вернёт
`ok=False`, сохранит порядок 7 и не добавит событие.

**Как проверено, что отказ безопасен?** Перед вызовом делается `deepcopy(state)`,
после отказа весь словарь сравнивается с копией.
